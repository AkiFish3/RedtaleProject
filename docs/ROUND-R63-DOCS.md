## 3. 新建 `docs/ROUNDS.md`（60 份轮次文档的唯一入口）

**触发**：写 T-0058 验收记录时发现，60 份 `ROUND-*.md` 除了 `PLAN.md` §13 那张大表以外**没有任何入口**。
机械扫描（文件名是否被任何其它 md 提到）实测 **31 份是孤儿** —— 也就是说 R20、R24~R28、R30~R33、R41~R62
这 31 轮的细节文档，除了「知道文件名」的人，谁也找不到。

**做法**：标题从每份文件首行机械抽取（`# R59 · 验收 T-0054 + …`），按轮次号排序；早期两份标题里没写轮次号
（`ROUND-M1-ATTR` / `ROUND-M3`）按时间顺序补成 **R2 / R3**。生成脚本是一次性的（`build/gen_rounds.py`，
不入库），正式化作为 **C9** 留在派单池。

**维护规则写进了文件头**：每轮新增一份 `ROUND-*` 就必须追加一行；不追加则 T-0059 的孤儿提示会点出来。

## 4. `CONTRACTS.md` §4.38 内部实现类登记（提示 17→0）

问题不在那 17 个类，而在「提示永远为真」：`check_contracts` 每次跑都吐同样的 17 条
（`Json5` / `ConfigStore` / `AttackSpeed*` / `Crit*` / `DamageRules` / `TargetClass` / `ScriptAction` /
`ConditionType` / `TriggerType` / `ItemUpgradeHooks` 等），真实效果是**把新信号埋掉**。

补一节 §4.38，三条约束写死：

1. **不是契约**——开头就写「不给 S8 当设计依据，只保证名字还在、文件还在」；
2. **理由给出**——`AttributeBreakdown` 的构造取过三次形态，写进契约等于把实现细节上锁；
3. **反向义务**——改类名必须同步本节，这正是 `check_contracts` 会红的地方。

结果：`共 39 条契约 · 28 个声明类 · 0 条提示 · 0 条问题`。

**声明类仍是 28** —— 因为工具只扫 `### 4.x` **标题行**，而 §4.38 的类名在表格正文里。
这条恰好自证了 R62-c 的口径（只扫标题行）没跑偏：正文里的名字参与「是否出现过」的反向判定，
但不参与「声明类」计数。

## 5. 派 T-0059（`check_docs.py`）

321 条路径引用（`docs/<名字>.md` / `tools/<名字>.py` / `src/...java`）现在**一条都没人校验**。R43 把
`/redtale probe` 改名 `selftest`、R59 把 `gen_attr_lang` 从整体覆写改成合并语义——这类改名之后
文档里就是死路径，而 `check_contracts` 只管类名、`check_defaults` 只管配置清单。

卡里同时钉死**不做什么**（这是本轮唯一的新增判断）：

| 不做 | 原因（实测） |
|---|---|
| `/redtale` 子命令字面量校验 | 基线 3 条假阳性：`/redtale affix` / `codex` / `inspect` 是「计划中」的提法 |
| 校验 markdown 链接锚点 | `#13.66` 这类锚点是章节号，不是文件路径 |
| 自动补 `ROUNDS.md` 的孤儿行 | 孤儿由 S7 补（工具只报），否则工具开始写文档就没边界了 |
| 扫 `docs/TASKS.md` | 卡板天生写「还没建的文件」（本卡自己的独占文件就是 `check_docs.py`），扫它等于每次派单都红一次 |
| 扫 `PLAN.md` 的正文与 `## 13.6x` 段 | 同因：那里的「下一步」写的是未来文件；**只扫 `| R` 台账行**（那是「已发生的事」） |

**这一条是写卡时踩出来的**（记在 §13.66 R63-e）：第一版把「全部 `docs/*.md` + `PLAN.md` 全文」都扫，
R63 自己写完全部文档后实测 **20 条红**，其中 19 条是「未来文件」（卡面独占文件、夹具示例 `NOPE.md`、待写的
`PROFESSION.md`…）。**一个基线就红的检查等于没有检查**，所以口径改成窄集合；同时给自己定了一条写法纪律：
**提到还没建的文件时不写 `tools/` / `docs/` 前缀**（写成 `check_docs.py` 而不是全路径），这条纪律让窄集合之外
的文本也不会骗人。
